Idea 2 · Durable state

The chef forgets. The kitchen remembers.

Every session starts blank — the model doesn't remember yesterday. If the app's reality lives only in the chat, you re-explain it forever. So the kitchen keeps books: push it to disk.

Idea 2 (cont.) · The ratchet

A green eval stays green.

Each new feature ships only if the whole suite still passes — so you never break an old requirement to land a new one. Like a dish that's cleared the tasting station: cleared for good.
▸

If a new change can break a passing eval without anyone noticing, you have no ratchet — the test suite is what notices.

🐢🚶🏃 the same 5 evals gate every version — a phase ships only if it still passes the ones before
Idea 3 · Two models, not one

Separate the builder from the judge.

Generator

Sonnet writes the app's answer.

Evaluator

Opus — different, stronger. Decides if it's good. Votes 3–5×, majority.

The chef doesn't taste their own plate — there's a separate taster on the pass."Separating the agent doing the work from the agent judging it proves to be a strong lever." — Anthropic, Harness Design for Long-Running Apps (2026) · a model grading its own work always says "looks great."
🏃 the cook = the app's Sonnet · the taster = judge() on a second pass (Opus)

Idea 4 · Workflow vs agent

The biggest design choice today.

Workflow

You set the steps.

Predictable · cheap to debug · easy to evaluate.

Agent

It picks its own steps + tools.

Flexible · hard to debug · harder to evaluate.

▸

A fixed prix-fixe menu vs a chef who improvises off the pantry.   Use the simplest thing that works — 🐢🚶 = workflow · 🏃 = agent.

🐢🚶 one-shot workflows · 🏃 the loop that chooses PubMedAnthropic, Building Effective Agents (Dec 2024)
